# Atomic companion-action drafts — 1.19

`CompanionBattleAction.prepare(Board, MoveBudget, int mode, int undos, CompanionBattle.State, int slot, boolean combo, int[] certifiedPlan)` returns a candidate session or `null`. The UI mode must be **0 (Journey) or 5 (expedition)**, the board must use progression version 6, and its budget must be the mode-0 relay policy. The caller separately checks current run identity, actual ownership and active UI request before accepting a draft.

The helper clones the board by replaying its saved history, compares the complete current mask/gates/action count, then reconstructs the existing budget with `restoreVersion`. The original board, ledger, input state and supplied plan remain untouched. A result contains independent mutable board and budget candidates, the new immutable companion state, updated undo count, exact IDs actually exited/restored, timed highlights and the companion’s effect/color. The caller must persist all candidate session fields in one existing save transaction, then publish them and trigger feedback; this helper performs no preferences write or visual effect.

For GUIDE, TRAIL, PULSE, FLOW and Resonance, a complete supplied plan is replayed from the current board through actual completion. A stale initial plan, a partial prefix, illegal later action, duplicate piece, manual gate, unknown ID or unsolved ending refuses the command before anything can reach the source session. There are **no solver calls** in this helper. The active controller can pass a cached plan; replay is bounded by the remaining U pieces.

GUIDE returns one exact hint and its definition duration. TRAIL returns up to the definition’s safe-prefix length and duration. VISION requires a currently legal piece, uses its own duration, and does not infer complete solvability. PULSE/FLOW execute actual certified exits through `MoveBudget.attempt`; each successful exit consumes the usual action and receives the state’s ordinary once-per-ID energy receipt. When fewer pieces remain, FLOW reports and performs only that shorter count. REWIND uses `MoveBudget.undo`, refunds actual history actions and increments the saved undo count; it retains credited exit IDs, so re-exiting a restored piece earns nothing again. A missing history or overflowing undo counter refuses the whole draft.

A ready Resonance uses the same complete-plan validation and performs one explicit certified exit. It marks the combo spent, charges no additional energy, consumes the ordinary board action, and may earn the ordinary first-exit energy receipt. A refused combo keeps readiness on the original state. A spent combo cannot run twice.

Every accepted result’s actual remaining certificate is then played through the real budget until the resulting board is solved. Those later mutations of the candidate still leave the complete source session unchanged.

The suite additionally checks both input and output snapshots, restored ledger/undo consistency, exact skill parameters and energy, used-member rejection, insufficient energy, missing/stale/partial/late-corrupt certificates, invalid slots and modes, incoherent ledgers, historical-board exclusion, solved/no-effect boards, actual legal-but-doomed positions for VISION, immobile dead ends, undo/re-exit farming, explicit ready/invalid/spent combos, and one-piece FLOW/TRAIL suffixes. Candidate boards retain zero populated planner cache entries after preparation, corroborating that validation does not search for a solution.

This is host execution of actual Java engine rules and draft preparation. It does **not** establish Android commit/rollback integration, saved-session lifecycle correctness, gesture/rendering quality, physical-device behaviour, human difficulty, enjoyment, retention, or provider acceptance. Native save-failure and UI work require their own evidence.
