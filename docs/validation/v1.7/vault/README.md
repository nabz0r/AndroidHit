# Account cosmetic vault — 1.7 candidate

The new native `.social.CosmeticVaultActivity` displays the premium account catalogue separately from earned LumaCoins. Its indigo/mint surface uses the game's original vector item art, native scrolling, wrapping Android text, one/two-column cards, system-bar insets, and English, French, German, Spanish, Portuguese and Italian copy. It is reached from the shop's LumaGold card. A Google connection is optional for playing; viewing this private server catalogue requires an authenticated Google account and an explicit **Load catalogue** action.

The client uses `BuildConfig.SOCIAL_API_BASE_URL` and `GET /v1/wallet/cosmetic-catalog`, independently of Play Billing activation. The response includes `balance`, `version`, the account's `owned` cosmetic IDs, consecutive duplicate count, server enable flag and the actual conditional probability for every item. The UI never invents an account balance or possession state before that authenticated response. Offline previews show item names/art and request a refresh for account ownership and probabilities.

## Paid operation remains closed

`BuildConfig.PAID_COSMETIC_DRAWS_ENABLED` is **false**. The server's `PAID_COSMETIC_DRAWS_ENABLED` remains false by default. Both must independently allow a draw; the Android button is disabled and the client refuses a draw before creating a pending request or requesting an ID token when the build gate is false. A catalogue response with `enabled:true` alone cannot activate payment. No live activation or real draw was performed as part of this work.

The prepared terms are 100 account **LumaGold** per draw, 50 LumaGold returned for an account duplicate, and an item new to the account on draw 20 after 19 consecutive account duplicates if an unowned account item remains. At that point the server removes owned IDs from the eligible pool and renormalizes the remaining weights. The UI displays those current probabilities per item, rounded to three decimal places, rather than continuing to show unconditional 60/30/10 rarity rates. With a complete collection, all items remain eligible and no new-item guarantee is claimed. All items change appearance only.

Account entitlements and locally earned wardrobe items are currently separate ownership sources. This premium pool includes the same 24 IDs, including local starter styles. An item already earned on this device may therefore be new to the account and receive the server's new-item treatment. The catalogue explicitly says **new to your account** and discloses this distinction. Before opening paid draws, the product should decide whether to unify earned/account ownership on the server or provide a separate premium pool; it must not promise an inventory-new item under the current contract.

## Request and ownership boundaries

The prepared `POST /v1/wallet/cosmetic-draw` sends only a validated, per-account idempotency `requestId`; it never sends a client price or reward decision. Its original ID is saved before token/network work and reused after a failed request or client recreation. A failed local commit blocks submission, including Android's memory-before-disk failure model. A pending receipt can be resumed even if an uncertain earlier debit reduced the current balance below 100; the server returns an existing receipt before checking funds for a new draw. It still requires both enable gates. No automatic new draw follows a result or network error.

Firebase ID tokens are sent only to the configured HTTPS origin. Redirect following is disabled, responses are limited to 128 KiB, and token acquisition, transport and delivery recheck the same account UID. Closing the activity cancels its client, disconnects active transport and ignores late callbacks. The single background worker has a bounded queue. No Google token or credential is saved or logged by this module.

`CosmeticVaultProtocol` rejects changed prices/compensation/guarantee/currency, gameplay benefits, incomplete or duplicated catalogues, unknown ownership IDs, incorrect conditional probabilities, nonfinite values, fractional/overflowed integer fields and a receipt for another request. A verified server result remains authoritative even if the optional local entitlement cache fails to persist; refreshing the authenticated catalogue restores it. That cache is keyed by hashed UID, preserves the latest wallet version, and is accessible only while that Google account is current. `CosmeticVaultClient.ownsCosmetic(Context,id)` supplies the wardrobe's external ownership; `clearCache(Context,uid)` removes it on logout/deletion. Pending uncertain receipts are retained separately for their original account.

No method reads or writes the local earned-coin ledger. The server decides the item, debit, duplicate return, guarantee and entitlements in one transaction.

- [1,552 passing protocol/client model checks](automated-checks.txt): actual offline server-generated catalogue/receipt payloads; base and guarantee-conditioned probabilities; invalid/overflow/missing fields; all 24 IDs and six translations; independent build/server gates; 1,000 build-blocked draws; stable retry IDs; client recreation; zero-balance receipt resume; memory-before-disk save failure; late token/account-change races; ownership isolation and close guards.
- [Server fixtures](server-fixtures.json) come from `CosmeticService` with an in-memory store and a deterministic test seed. They are synthetic account data generated locally, not a capture of a production user or real purchase.
- [Independent SDK source compilation](sdk-source-compile.txt) passes against Android SDK 36, Firebase Auth 25.0.0/Auth Interop 20.0.0, Google Tasks 18.4.0/Basement 18.9.0 and the real generated closed Lab build configuration. Temporary compiler output does not build or alter an APK.

Run `scripts/test-cosmetic-vault-v17.sh`; the JSON JAR can be supplied through `LUMA_JSON_JAR` or resolved from the existing local Gradle cache. Mutable paid switches occur only in the JVM test adapter; production build configuration is independently checked to remain false. The tests make **no real sign-in, ID-token acquisition, HTTPS request, purchase, LumaGold debit or device-rendering claim**. Final Gradle packaging, native screenshots, authenticated production-catalogue availability and any future paid checkout require separate qualification. A production catalogue may correctly return “not deployed yet” until its server release is deployed.
