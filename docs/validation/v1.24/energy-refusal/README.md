# Reprise d’un refus de recharge Lab — correction locale 1.24

Le [readback natif B](../native-lab/b01-upgrade-discovery/native/retained-after-ui.json) contient 0 LumaGold test, 0 recharge et une outbox `SPEND` héritée de E. Le [PNG natif original](../native-lab/b01-upgrade-discovery/native/session-energy-fr.png) montre 4 énergies régénérées et «Confirmation en attente». Le refus n’a débité ni accordé de recharge : sa reprise transformait `wallet_insufficient` en `commerce_save_error`, laissant l’intention non résolue.

Le correctif touche uniquement `wallet/EnergyPurchaseJournal.java` et `EnergyPurchaseController.java`. En Lab, le journal vérifie d’abord le marqueur atomique d’un paiement déjà effectué. Si le paiement n’a jamais été enregistré et que le solde local est insuffisant, il sauvegarde un état terminal `REFUSED`, avec les mêmes UUID de dépense et d’usage, avant d’annoncer «LumaGold insuffisants. Aucun nouveau débit». Une reprise à froid conserve ce refus. Seule une nouvelle confirmation explicite peut créer une autre demande.

Un `SPEND` déjà payé reste récupérable à 0 Gold : son pack passe à `USE`, attend l’énergie à zéro si nécessaire, puis crédite ses dix points avec le reçu existant. Une écriture de refus échouée reste une véritable erreur de sauvegarde jusqu’à sa reprise durable. Les erreurs HTTP de production ne sont jamais transformées en refus terminal ; elles gardent leur outbox et leur UUID de retry. Aucun endpoint, prix, plafond, règle d’énergie, paiement réel, publicité, rang ou copie n’est changé.

- [Avant qualifié](before-fix-qualified/receipt.json) : les deux classes originales sont copiées et vérifiées contre les hashes du candidat B. Le test reproduit `SPEND`, `commerce_save_error` et le message de confirmation en attente.
- [Après final](after-fix-final/report.json) : **6 194 assertions PASS**, **400 échecs d’écriture** dans les deux comportements mémoire/disque, **202 reconstructions froides**, deux groupes de **32 handles concurrents** pour refus puis paiement. Le vrai `SessionEnergyStore` régénère quatre unités via ses API ; aucun compteur d’énergie factice. Le transport réseau est un adaptateur explicite de callbacks.
- [Régressions](regressions/receipt.json) : 84 contrôles controller/journal et 36 contrôles du vrai client HTTP avec connexions/Firebase simulés. Aucun socket ou paiement réel.
- [Revue indépendante ciblée](independent-review.json), [diff local](local-source.diff), [sources du lot](source-snapshot/manifest.json) et [historique des tentatives](attempt-dispositions.json).
