# Typed recovery after repeated local-save failures

The UI needs to distinguish a retryable local transaction failure from an unrelated `IllegalStateException`. `GameStore.LocalSaveException` extends that existing type, so older handlers remain compatible. `LocalSaveTransactions.write` and `flush` now use the subtype without changing their pending map, commit ordering, amounts, receipts or error text. A public synchronized `GameStore.retryPendingLocalSave()` flushes the exact pending transaction for **that GameStore preference file**; it does not rerun its original purchase, reward or inventory grant.

Run `bash scripts/test-local-save-v19.sh`. The [executed summary](summary.json) records **229 assertions across 13 scenarios**, with **44 forced commit failures** and up to **four consecutive failures** in one scenario. Both memory-before-disk modes are covered. [failure-trace.csv](failure-trace.csv) identifies each initial write, failing read/flush and explicit retry, with the durable map required to stay unchanged while writes fail.

The real public APIs exercise a power trial, a solved Guardian's 100-coin reward, the completed tutorial's 100 coins/two hints, avatar styling, immediate process reconstruction, shared exception compatibility for MetaProgress, and concurrent retries from two GameStore handles. Reads such as stock, available trial, receipt, balance and style must surface the typed exception when they cannot flush a pending write. Once storage succeeds, the original receipt and exact stock/currency become durable once; another claim or cold replay cannot add a second reward. Process death before that durable retry exposes only the last complete on-disk map and permits exactly one subsequent claim.

MetaProgress uses a different preference file. Its pending transaction uses the same typed failure, but `GameStore.retryPendingLocalSave()` intentionally does not flush that other file. A later MetaProgress read or record operation retries its own pending transaction. The test checks this boundary instead of silently broadening the new API.

Seven existing suites were rerun without relaxed expectations: [regression/summary.json](regression/summary.json) binds their logs and current Java source hashes. They cover Journey reward/trial/grading policy (65,736 checks), Guardian/store/style integration (5,146), economy (6,611), data (8,882), meta/journal (362), tutorial (1,454), and rewards/cosmetics (100,953). The [source manifest](source-inputs.json) identifies the new helper/type and harness inputs.

These are JVM contracts using the established Android preference adapters. They establish transaction/retry behaviour, not native error-panel input, real filesystem fault handling, activity rotation, flash durability, provider access or revenue. The installed UI's typed error boundary, Retry touch ownership and navigation guard require their separate native fault evidence.
