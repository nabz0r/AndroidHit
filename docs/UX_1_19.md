# Puzzle squad and lively presentation — 1.19

The owner requested all three avatar improvements: a squad that matters during puzzles, distinct companion skills, and a more responsive presentation. The implementation connects an owned companion to an explicit puzzle action; collecting or changing an outfit alone does not silently grant a skill use, consume a power-up, or alter the selected team.

This is the implementation contract and scoped host evidence. Final APK, visual review, actual run-controller tests, and release status belong to the versioned release evidence when recorded. The earlier browser mockup and 1.18 owner feedback remain historical; neither is Android acceptance of this work.

## Team selection

A puzzle squad has one to three distinct owned companions, in a deliberate order. The first is the captain. A legacy profile begins with only its equipped owned companion; other owned, purchasable, or unowned companions are never added automatically. Free slots invite an explicit choice.

`GameStore.companionSquad()` returns an immutable snapshot. `setCompanionSquad(List<String>)` validates the complete selection, then saves just the ordered ID list in `companion_squad_v119`. A full invalid request is refused rather than partly accepted. Team editing neither purchases a character nor changes the equipped appearance, copies, gear, stock, coins, or account currency. Once a team is explicitly saved, equipping a different appearance does not overwrite it.

If account ownership becomes unavailable, reads omit those saved members without rewriting the durable team. Restored ownership restores their saved order. Unknown IDs, duplicate entries, empty entries and excess members are filtered from damaged saves; an empty result falls back to the equipped owned companion, then the guaranteed starter. A wrong-type value for this new key also falls back safely. This recovery does not grant ownership.

The active attempt keeps its starting squad. Team edits during a puzzle apply to the next attempt, and the interface must state that boundary. The captain is the first team member, not an implicit command to replace the wardrobe appearance.

## What each role does

The detail screen takes the actual skill definition’s amount, duration in seconds, and energy cost. It shows those values before activation; effects should never be inferred from rarity or costume art.

| Role | Action shown to the player | Limits to communicate |
| --- | --- | --- |
| GUIDE | Highlight one certified safe next action | Timed guidance, not an automatic move |
| VISION | Highlight immediately movable pieces | Local legality does **not** certify a complete solution |
| TRAIL | Preview a short sequence of certified safe actions | Timed preview; amount comes from the companion definition |
| PULSE | Execute one certified exit | The usual action budget applies |
| FLOW | Execute a short certified action sequence | The usual action budget applies; execute up to the declared amount |
| REWIND | Undo earlier historical actions | Bounded by the remaining undo allowance |

Each companion can use its skill once in an attempt. The team shares attempt-local energy. Every distinct piece that exits adds one energy, including an automatic exit; undoing and exiting that same piece again adds nothing. A refused activation with no eligible target spends no energy. Existing power-up stock is a separate inventory, and companion skills do not spend it.

Using two skills from different role families charges **Resonance**. The player then explicitly activates one certified action, once per attempt. Two appropriately different companions are sufficient; a full team of three is not required. The UI needs separate locked, ready and used states, together with the reason a command is unavailable.

## Implemented portrait and reaction layer

The Android dock composes the actual companion’s current form with the selected style and presented wardrobe, using the existing authored portrait renderer. It samples happy, surprised, thinking and jump/stance poses from actual success, blocked gestures, gate changes and skill activation. Selected board pieces influence facing; reduced motion keeps stable frame choices and restrained effects. The six family effects are brief and clipped to the board. This reuses existing authored art; it does not add37 unique engines or a new animation atlas for every role.

The implemented skill page separates looking from activation, shows current energy and the real role parameters, and reports locked, ready and used states. Navigation and lifecycle/save-failure paths require exact-candidate native qualification. The dock’s shared geometry reserves the physical touch floor instead of treating a decorative portrait as an undocumented small button. Per-companion apparel fitting and physical-device comfort remain unqualified.

## Readable feedback and motion

A selected companion should show its portrait, role, exact energy cost and ready/used state alongside the board. Preview and activation remain different actions. A brief reaction should explain the outcome of a successful move, blocked gesture, charged skill or Resonance rather than cover the board or imply a successful action when none occurred.

The implemented team screen exposes selected slots, owned/locked choices, explicit save, and a route back to the current puzzle. The first slot is the captain; the team description states that order. Returning from a detail view should preserve the board and its action accounting. Cosmetics retain their authored appearance; copy explicitly says that the companion determines the puzzle skill and outfits change the look.

`V119Strings` supplies these contracts in English, French, German, Spanish, Portuguese and Italian. Timed descriptions use actual seconds, numeric costs are formatted from the current definition, and Vision’s uncertainty is retained in every locale. The French labels favour short action language: “Équipe”, “Talent de puzzle”, “Résonance”, “Activer”.

## Persistence and verification

Team storage uses the existing `LocalSaveTransactions` lock and retry path. Android can update the in-memory preferences map before a disk commit fails. The write therefore retains the exact team selection for a retry and raises the typed `GameStore.LocalSaveException`; neither an uncommitted in-memory value nor an unrelated new request is treated as successful persistence. Guarded reads and edits settle pending work before continuing. A process killed before that retry recovers the previous durable selection.

Run `scripts/test-squad-store-v119.sh`. The current result is **799 passing JVM assertions** against the real `GameStore` and production data/engine classes, using an explicit durable-preferences adapter. [Recorded output](validation/v1.19/squad-store/host-checks.txt).

The checks cover every current Catalog identity, one-to-three bounds, duplicates, invalid/unowned requests, legacy defaults, mutable inputs, immutable return values, equipped-appearance independence, account ownership loss/restoration, damaged and wrong-type values, both refused-commit models, repeated refusals, another store handle, pending purchase/team interleaving, cold recreation, and 120 concurrent team edits. Complete-save comparisons show that team changes affect only the new team key. All six language dictionaries are formatted, including role amounts, seconds and energy, with explicit checks that Vision does not claim certified solvability and Resonance does not require three companions.

These are storage and copy checks. They do not establish the final run controller’s correctness, Android drawing and gesture behaviour, every translated line’s visual fit, physical-device comfort, perceived impact, retention, or commercial acceptance. Those claims require their own recorded evidence and player review.
